## 4. Root Cause Analysis

The main classification problem is that InfraNodus exposes the same semantic
kernel through many applications. "SEO analysis", "survey analysis", and
"research ideation" are not three unrelated engines. They are compositions of
source ingestion, text normalization, graph construction, community detection,
gap analysis, evidence retrieval, optional AI generation, and export.

A flat list also conflates four different kinds of statement:

- capability: an operation the product performs;
- workflow: a composition of capabilities for a user outcome;
- integration: an alternate control or data surface;
- quota: a plan-dependent bound, not a semantic feature.

The ontology resolves this by assigning each item a layer and plane and by
making interactions explicit.

## 6. Patterns & Anti-Patterns Discovered

Patterns:

- One graph kernel supports many domain workflows.
- The interactive graph is both an output and a control surface for retrieval
  and AI attention steering.
- Structural-gap detection is the recurring differentiator across research,
  SEO, market analysis, ideation, and GraphRAG.
- Provenance-preserving navigation links global graph observations back to
  source statements.
- API, MCP, browser, Obsidian, and IDE extensions are alternate adapters over
  the same analysis capabilities.

Anti-patterns:

- Treating every use-case page as a distinct feature.
- Reporting a generated AI answer without the graph or source evidence path.
- Treating "unlimited per month" as unbounded operation despite per-item,
  hourly, weekly, import, live-feed, and stored-graph limits.
- Assuming private hosting implies on-premise or self-hosted deployment.
- Treating public marketing copy as proof of account-only behavior.

## 9. Architectural Observations

InfraNodus can be denoted as a staged transformation:

```text
heterogeneous content
  -> normalized statements and concepts
  -> attributed knowledge graph
  -> network observations and structural gaps
  -> human exploration and optional graph-grounded AI
  -> exported evidence, decisions, prompts, or downstream automation
```

The semantic center is not the LLM. It is the attributed graph plus the
mapping from graph elements back to source statements. AI generation is an
optional observer and recommender over that structure. This distinction is
important for provenance, privacy, reproducibility, and integration design.

## 12. STAMP & Constitutional Alignment

The ontology identifies these controllers:

## 17. Decision Record

Three implementation shapes were assessed:

- a pixel clone was rejected because visual imitation is brittle and does not
  prove semantic parity;
- separate mini-tools were rejected because they fragment project, filter,
  provenance, and revision state;
- a capability-equivalent OCaml workspace was selected because one typed graph
  can support every view, workflow, integration, and evidence observer.

The selected architecture retains Dream, Bonsai, js_of_ocaml, the harness `Db`
actor, and direct `ocaml-playwright`. No authored JavaScript, Python, shell, or
direct database client is introduced. Provider-backed imports and AI use typed
OCaml adapters. Their complete UI and contract can be tested with deterministic
fixtures; absent credentials produce explicit unavailable states.

This journal captures the requirements, evidence, alternatives, decisions,
constraints, and implementation implications. It does not contain private
hidden chain-of-thought. The full reviewable technical rationale is preserved
as explicit engineering decisions here and in the design specification.
