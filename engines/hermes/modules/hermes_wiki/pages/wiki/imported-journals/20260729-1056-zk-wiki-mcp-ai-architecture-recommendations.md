# ZK/Wiki System Architecture: Agentic MCP & AI Integration

*Date: 2026-07-29*
*Context: Discussion and recommendations regarding the integration of Semantic Search, AI/ML tools, and MCP access into the existing OCaml-based Zettelkasten (ZK) and Wiki harness.*

## 1. Initial Assessment (Strict OCaml-Only Boundary)
The initial review of the ZK/wiki architecture (`skills/wiki-design`, `docs/harness-wiki`, and `docs/zk`) confirmed a rigorous design. The wiki generator is a pure OCaml `Model → View` kernel powered by SQLite and Git. It enforces Notion-style 2-way navigability (sidebars, breadcrumbs, backlinks) and leverages network science (PageRank, spanning trees) and TF-IDF for semantic similarity directly within the deterministic harness. 

**Initial Implications (Strict Boundary):**
*   **Classical Information Retrieval (IR):** Semantic search must fall back to highly optimized, deterministic classical algorithms implemented from scratch in pure OCaml (TF-IDF, BM25) rather than deep-learning embeddings.
*   **No Neural Embeddings / No WASM:** Reliance on external APIs or embedded quantized LLMs via Python/Rust/WASM bindings pollutes the pure OCaml shell and compromises the standalone determinism of the Tier-1 judge.

**Initial Recommendations:**
1.  **OCaml-Native BM25 Semantic Search Engine:** Implement Okapi BM25 ranking natively in OCaml for dependency-free semantic search.
2.  **Homomorphic Integration of Search State into SQLite:** Calculate the BM25 matrix during the harness execution gate and commit it as a deterministic BLOB/table into SQLite to prevent blocking the zero-trust gate.
3.  **QCheck Laws for Semantic Search:** Introduce QCheck properties (Reflexivity, Monotonicity) in the OCaml test suite to verify the search algebra.
4.  **Automated Ontology Inference:** Use pure OCaml community-detection algorithms (e.g., Louvain) to automatically generate "Maps of Content" (MoCs).
5.  **Rete-UL Validation for Knowledge Decay:** Introduce rules to measure "Knowledge Decay" (time elapsed $\times$ topological mutations) to flag stale Decision Records (ADRs).

## 2. Refined Assessment (External AI/ML Orchestrated via OCaml Allowed)
Upon clarification, the OCaml harness is permitted to orchestrate external AI/ML tools, lookups, and embeddings. The OCaml layer acts as the deterministic coordinator (C3I daemon) while delegating heavy semantic lifting to specialized ML tools.

**Updated Fractal Mapping:**
*   **Stratum A (Algebraic Core - OCaml + Vector Space):** Carrier Set includes `note`, `graph`, and `vector` ($\mathbb{R}^n$). Semantic Domain expands to the union of the explicit Markdown link graph and implicit semantic vector space.
*   **Stratum B (Engines - External ML Orchestration):** OCaml delegates to external LLM/ML embedding APIs or local fast binaries (e.g., `ollama`, `llama.cpp`) to compute semantic vectors, acting as a robust wrapper for serialization and error recovery.
*   **Stratum C (Safety / Rule Fractal - Rete-UL):** UCAs include external ML tools hanging or introducing non-determinism. Mitigated by strict circuit breakers and SQLite memoization (identical Git hashes strictly yield cached vectors).

**Updated Recommendations:**
1.  **Integrate SQLite Vector Storage (`sqlite-vss` or BLOBs):** Store vectors generated by external ML tools directly in `harness/state/zigvm_harness.sqlite3`. Loading the `sqlite-vss` extension allows lightning-fast $K$-nearest neighbor (KNN) searches, offloading math from OCaml.
2.  **LLM-Assisted Ontology Generation (MoC):** OCaml passes ZK sub-graphs to an external LLM to automatically synthesize MoC pages, validating the returned Markdown before injection.
3.  **Circuit-Breaker Pattern for AI Tools:** Implement strict timeouts in OCaml. If an external embedding API fails, the harness gracefully falls back to the SQLite cache, ensuring the canonical validation gate never turns RED due to network failure.
4.  **Automated Semantic Conflict Detection:** Use external ML to run semantic diffs between new notes and the corpus. Contradictions generate a `Semantic_Conflict` fact in SQLite, intentionally failing the Rete-UL gate until resolved.

## 3. MCP Integration Assessment (Agentic Access)
The absolute requirement is that the Wiki and ZK must be fully accessible for agent-based MCP (Model Context Protocol) access. The OCaml harness (`zigvm-harness`) acts as the MCP server and must expose the Zettelkasten directly to agents.

**MCP Recommendations:**
1.  **Expose ZK Read/Search Capabilities as MCP Tools:**
    *   `zk_search(query)`: Uses the semantic embedding engine to return relevant notes, UUIDs/slugs, and excerpts.
    *   `zk_read_note(slug)`: Returns the full Markdown content along with structured metadata (inbound backlinks, outbound links, PageRank score).
    *   `zk_graph_neighborhood(slug)`: Returns the immediate topological neighborhood, allowing agents to "walk" the graph without reading massive files.
2.  **Enable MCP-Driven ZK Authoring (Write Access):**
    *   `zk_record_decision(title, context, decision, implications)`: Generates a correctly formatted ADR Markdown file with a UUID and inserts it into `docs/zk/`. The OCaml harness applies Zero-Trust validation to ensure no dead links are introduced.
3.  **Agentic "Context-Injection" upon Boot:**
    *   Provide a `zk_system_context()` tool. When an agent boots for a specific task, the harness automatically runs a semantic search against the ZK using the task's title and injects the top architectural constraints into the agent's prompt envelope.
4.  **Automated Graph Healing via MCP:**
    *   Expose `zk_get_anomalies()` to identify orphaned notes or conflicting semantic clusters. Agents can periodically call this as a background maintenance task to synthesize connecting MoC pages and heal the Zettelkasten.

## 4. Deep Analysis: ACH, Reality Check, and Devil's Advocate
Evaluating the proposed ML-augmented MCP architecture requires confronting the inherent friction between a deterministic Tier-1 judge (OCaml) and stochastic tools (LLMs).

**Devil's Advocate & The Hallucination Lockout:**
If an ML tool is integrated directly into the `record_cycle` gate (e.g., detecting contradictions to pass/fail a commit), the system loses determinism. A hallucinated contradiction from an LLM could permanently lock the repository in a `RED` gate state. Furthermore, ML APIs have latency—stalling a local developer loop to vectorize a Markdown file violates the fast-feedback requirement of a Tier-1 judge.
*Resolution:* AI must be strictly separated from the validation path. Embedding generation and LLM MoC synthesis must be asynchronous background cron jobs or explicit MCP tool invocations by an agent, never blocking steps for a `zigvm` code commit.

**ACH: File-Level vs. Block-Level Embeddings**
*   *Hypothesis A (File-Level):* Easy to implement, but dilutes semantic meaning. A long ADR might contain 5 unrelated constraints.
*   *Hypothesis B (Block-Level, Roam/Logseq approach):* Precise. The OCaml parser chunks files by headers/paragraphs, storing vectors per block.
*   *Verdict:* Hypothesis B is vastly superior for agentic workflows. When an agent queries `zk_search()`, it needs the exact paragraph containing the constraint, not a 2000-word document.

## 5. Web-Inspired Advanced ZK Features for MCP

Based on modern PKM (Personal Knowledge Management) ecosystems (Obsidian, Logseq, Roam) and Semantic Graphs (Neo4j, InfraNodus), the following features should be implemented in the OCaml harness:

1.  **Typed Relational Edges (Semantic Graphing):**
    Instead of generic links (`A -> B`), implement typed links (`[[supports: Architecture]]` or `[[contradicts: E9_Plan]]`). The `zk_graph_neighborhood` MCP tool can then inform agents *how* nodes relate, enabling logical reasoning over the graph.
2.  **GraphRAG (Retrieval-Augmented Graph):**
    Instead of simple vector similarity, `zk_system_context()` should traverse the graph. It finds the semantically nearest node and walks its typed edges (up to 2 hops) to synthesize a multi-document summary context for the agent.
3.  **"Unlinked Mentions" Discovery (Obsidian Style):**
    OCaml deterministically scans the corpus to find where a note's title is mentioned but not linked. The MCP tool `zk_get_unlinked_mentions()` allows an agent to verify the context and automatically inject the `[[link]]`.
4.  **Structural Hole Detection (InfraNodus Style):**
    Leverage pure OCaml network science (Betweenness Centrality) to identify "structural holes" (clusters with no bridges). The harness prompts agents via MCP to synthesize an ADR that bridges the two disconnected architectural domains.

### 6.2 The real gap: MCP exposure (Section 3 is 0% implemented)

`mcp_server.ml` registers exactly five tools: `facts`, `observe`, `next_slice`,
`record_cycle`, `log_ooda`. Every ZK capability lives behind HTTP on :8088 only —
invisible to MCP agents. Because the pure kernels already exist, the MCP slice is thin
glue, in priority order:

1. **`zk_search(q, k?, metric?)`** → wrap `docs_search_json` verbatim.
2. **`zk_read_note(slug)`** → wrap `api_note` (already returns mentions, inferred,
   similar, typed edges, blocks, html).
3. **`zk_neighborhood(slug, hops≤2)`** → new ~30-line pure function over
   `outlinks ∪ backlinks ∪ typed ∪ mentions`, returning edge-labelled JSON.
4. **`zk_anomalies()`** → orphans (degree 0), broken links, unlinked-mention pairs,
   stale `next_review` — `--wiki-audit` already computes `wiki_parity/broken_links/orphans`
   into SQLite; this tool re-serves that ledger row + the mention pairs.
5. **`zk_author_note` / `zk_record_decision`** (write path, LAST) → reuse
   `authored_note` / `decision_markdown` + `path_is_safe` + etag guard. This extends the
   `CTRL-ZK-AUTHOR` controller to a second entry surface ⇒ **mandatory STPA/UCA packet
   update** per `skills/stpa-safety-protocol` before landing.

Operational caveats: the h-mcp-staleness rule applies (reconnect after harness rebuild);
each MCP tool should have a CLI mirror flag so Zero-Trust evidence never depends on the
long-running server; every tool result must carry the source commit hash it was computed
from (same honesty discipline as `record_cycle`).

### 6.3 Block-level vectors (close §4's ACH-B properly)

`note_tokens` embeds whole notes. Enhancement: a pure chunker (split on headings /
blank-line paragraphs, attach any `^id` anchor, synthesize stable ids for anchor-less
blocks from a content digest), then reuse the *same* `Vec.embed` per chunk and key
`note_vectors` rows as `slug#^block`. `zk_search` gains a `granularity=block` mode that
returns the exact paragraph + parent slug. Laws to ship with it: (a) chunking is a
partition — concatenated chunk texts token-equal the note body; (b) determinism — same
raw bytes ⇒ same chunk ids and vectors; (c) a query matching one block ranks its parent
no lower than file-level search did (no-regression). Still zero ML, zero new deps.

### 6.4 GraphRAG = compose two things that already exist

`zk_system_context(task_text)` needs no new theory: KNN seed via `docs_search_json`'s
kernel → walk typed+untyped edges ≤2 hops with per-hop score decay (e.g. ×0.5), dedupe,
return top-K blocks (once 6.3 lands) with their relation paths
(`seed —supports→ X —contradicts→ Y`). Pure function over `page list` + vectors; laws:
bounded output size, hop-monotone score decay, determinism. The typed relations are what
lift this above flat RAG — an agent can be told *why* each context item is present.

### 6.5 Community detection & structural holes (the one genuinely new algorithm)

The only §5 item with no existing substrate. Recommendation: **deterministic label
propagation** (fixed iteration order, lexicographic tie-break) over Louvain — Louvain's
order-sensitivity fights the Tier-1 determinism requirement for marginal quality gain at
~130 nodes. Add Brandes betweenness (O(VE), trivial at this scale) for bridge scoring.
Outputs: (a) cluster id per note → replaces the degree heuristic in `mocs` with
community-grounded MoCs; (b) cluster pairs with zero connecting edges + the
highest-betweenness near-miss nodes → new rows in `zk_anomalies()` as "structural hole:
synthesize a bridging ADR". QCheck laws: partition validity (every node exactly one
label), determinism across runs, singleton graph ⇒ singleton cluster.

### 6.6 Knowledge decay as non-gating Rete facts (§1.5, done safely)

Frontmatter already carries `last_verified` / `next_review`. During `--wiki-audit`, emit
`note_stale(slug, age_days, pagerank)` facts into the Rete working memory; a rule flags
high-PageRank stale ADRs into the report. **Report-only, never gate-red** — this is
exactly the §4 lockout resolution applied in advance: staleness is a prompt for an agent
maintenance pass (via `zk_anomalies`), not a commit blocker.

### 6.7 External ML: keep the seam, defer the plug

Honest assessment: at the current corpus scale (~130 notes) deterministic hash-TF-IDF
KNN is empirically adequate, and every §2 risk (latency, non-determinism, hallucinated
conflicts) buys little. If neural embeddings are ever wanted, the seam already exists:
`note_vectors` is deliberately in sqlite-vector storage shape — an *offline* agent job
can write `kind='neural'` rows beside the deterministic ones, with fallback-to-TF-IDF as
the circuit breaker, and the gate never learns ML exists. `Semantic_Conflict` detection
(§2.4) should surface as an anomaly/report fact, **not** a gate-failing fact — a
hallucinated contradiction must never be able to hold the repo RED.

## 7. Web-Sourced Creative Catalogue (Claude ultrathink pass, 2026-07-29)

A survey of the 2025–26 landscape — GraphRAG research (arXiv 2501.13958 survey,
Microsoft GraphRAG, HippoRAG 2), agent-memory systems (Zep/Graphiti, A-MEM arXiv
2502.12110), discourse graphs (Joel Chan), and the PKM frontier (Obsidian
Dataview/Datacore/Bases, Roam/Logseq block refs, Tana supertags, InfraNodus, Andy
Matuschak's evergreen notes) — mapped onto what `docs_wiki.ml` actually has. Each idea
below names its source, its OCaml carrier, and its law shape. Everything here stays
deterministic; nothing touches the gate's red/green semantics.

### 7.1 Personalized-PageRank retrieval (HippoRAG's core trick — nearly free here)

HippoRAG's headline result is that **Personalized PageRank over a knowledge graph beats
flat vector KNN for multi-hop retrieval**. The wiki already has both halves:
`pagerank_core` (docs_wiki.ml:967) and query→node matching (`docs_search_json`). The
composition: seed the teleport vector with the query's KNN hits (weight ∝ similarity)
instead of the uniform vector, run the *same* power iteration, rank by stationary mass.
This retrieves notes that are *hub-connected to what matched*, not merely lexically
similar — multi-hop retrieval without any LLM. ~20 lines: `pagerank_core` just needs a
`?teleport` parameter. Laws: uniform teleport ⇒ identical to current PageRank
(degeneration law); Σ=1 stochasticity (already QCheck'd); determinism. This strictly
upgrades §6.4's GraphRAG walk — PPR *is* the principled version of "walk 2 hops with
decay".

### 7.2 Hybrid lexical+vector ranking via Reciprocal Rank Fusion

The industry-standard answer (Elastic, et al.) to "TF-IDF or embeddings?" is *both*,
fused by RRF: `score(d) = Σ 1/(60 + rank_i(d))`. Add a pure-OCaml BM25 scorer (§1.1
proposed it; ~40 lines given `corpus_idf` exists) beside the Vec KNN, fuse by rank.
RRF is tuning-free, scale-free, and deterministic — ideal for a Tier-1 judge. Law:
a document ranked #1 by both scorers is ranked #1 by the fusion (unanimity); fusion of
a ranker with itself is order-equivalent to that ranker.

### 7.3 The bi-temporal knowledge graph is already in the repo — it's called git

Zep/Graphiti's differentiator over GraphRAG is **bi-temporal edges** (when a fact was
true vs. when it was recorded) with non-destructive invalidation. The creative
realization for this repo: *git history already is the transaction-time axis, and the
harness already shells out to git*. Mine `git log --follow -p docs/` once per audit to
derive, for every note and every `[[link]]`/typed edge, its `(added_commit,
removed_commit?)` interval into a SQLite `edge_history` table. That unlocks:
`zk_graph(asof=<commit>)` (the concept graph as it stood at any commit — perfect for
"what did we believe when DIVERGENCE 540 was open?"), edge-removal events as
first-class "belief invalidated" facts, and knowledge-decay (§6.6) computed from *edge
churn around a note* rather than wall-clock alone. Pure kernel over `git log` output;
laws: intervals are well-formed (add ≤ remove), `asof(HEAD)` = current graph
(round-trip), monotonicity (history only grows).

### 7.4 A-MEM inverted: the ZK as the agents' long-term memory organ

A-MEM (NeurIPS '25) gives LLM agents a *Zettelkasten-shaped* memory: atomic notes,
auto-generated contextual links, memory evolution. This repo can run the arrow the
other way — the ZK already renders git+SQLite as a "System Memory" view
(`Docs_wiki.memory`, `mem_related`), so make it *writable* by the loop itself: after
each `record_cycle`, an auto-drafted **session note** (slice, verdict, DIVERGENCE ids,
touched modules, OODA excerpts) lands in `docs/zk/` via the existing `authored_note`
path with `verified_by: harness`, auto-linked by the existing mention-scan. The
Zettelkasten then *is* the episodic memory A-MEM builds externally — versioned,
law-checked, and greppable. Combined with §6.2's `zk_system_context`, an agent booting
on a slice retrieves its predecessors' actual reasoning, not just ledger rows.

### 7.5 Discourse graphs: the highest-leverage schema for an engineering ZK

Joel Chan's discourse graphs decompose knowledge into **question / claim / evidence**
nodes joined by **supports / opposes** edges — exactly the epistemology this project
already practices informally (ADR criteria envelopes, DIVERGENCE verdicts, mutant
kills). The carrier is trivial: a `type:` frontmatter key (the meta parser exists) +
the existing typed-edge syntax (`[[claim-X|@supports]]`). What it unlocks is the
queryable argument: `zk_argument(slug)` returns the evidence tree under a claim, and
**Rete rules can check discourse well-formedness** — a `claim` with zero inbound
`@supports` evidence edges, or a `decision` whose supporting claim was since
`@opposes`-linked, becomes a *report-only* anomaly (§6.6 discipline). Evidence nodes
can cite ledger rows (`harness_runs`, `MUTATION_LOG`) — claims literally backed by the
SQLite ground truth. This is the feature that makes the ZK an *argumentation system*
rather than a document pile.

### 7.6 Supertags / typed notes with fail-closed schemas (Tana / Capacities / Bases)

Tana's supertags and Obsidian's new Bases converge on the same idea: **notes are typed
objects with per-type required fields**. The harness already fail-closed-validates
skill frontmatter, so extend the same machinery: a `zk_schemas` table (or a schema note)
declaring e.g. `adr ⇒ requires {status, criteria, decision}`, `runbook ⇒ requires
{trigger, steps, rollback}`; `--wiki-audit` validates typed notes against their schema
(report-only at first, gate-red only if ever promoted deliberately). Auto-generated
type views ("all ADRs with status", "all open questions") fall out of §7.7's queries.

### 7.7 Saved queries as notes (Dataview/Datacore, made total and law-tested)

Obsidian's Dataview proved that *queries embedded in notes* turn a wiki into a
database; its successor Datacore and core Bases confirm the demand. OCaml version: a
tiny **total** query DSL in fenced blocks —

    ```zkquery
    from type:adr where status=flagged_for_review sort pagerank desc limit 10
    ```

— parsed by a pure combinator parser, evaluated against `page list` at render time,
displayed as a table (and served through MCP as `zk_query(q)`). Because queries are
notes, they are versioned, reviewed, and mention-scanned like everything else. Laws:
totality (every parse either errors cleanly or terminates — no recursion in the
grammar), monotone `limit`, filter-commutativity. This subsumes a dozen bespoke index
pages and gives agents a structured read API beyond search.

### 7.8 Block transclusion `![[note#^id]]` (Roam/Logseq's "killer feature")

Block *addressing* exists (`block_ids_of`); block *embedding* doesn't. Render
`![[slug#^id]]` by inlining the referenced block with a provenance chip linking back.
The classic failure mode is cycles — so the law is the interesting part: the
transclusion relation must be a DAG (reuse `reach_core` for the acyclicity check;
a cycle is a build-time anomaly), and rendering is depth-bounded. Combined with §6.3
block vectors, an agent's `zk_search` hit, the human's reading view, and the embedding
unit become the *same* block — one addressing scheme end-to-end.

### 7.9 Evergreen maturity + deterministic spaced review (Matuschak)

Evergreen-notes practice grades notes by maturity (seedling → budding → evergreen) and
revisits them on a schedule. Map maturity onto the existing `status` vocabulary
(additively), and drive review scheduling **deterministically from ledger events**
rather than wall-clock alone: a note's review interval doubles on each `verified_by`
touch (SM-2-shaped growth) and *resets when §7.3's edge-churn spikes around it* — i.e.
the graph disturbing a note's neighborhood is what schedules it for human eyes.
Surfaces as a "due for review" queue in `zk_anomalies()`, PageRank-weighted. Report-only.

### 7.10 Contextual backlinks (Roam-style)

Backlinks today are bare slugs. Store, per backlink, the *containing block's text*
(the sentence around the `[[link]]`) at `build` time — render it in the backlink panel
and return it in `api_note`/`zk_read_note`. For agents this is disproportionately
valuable: the context of a citation often answers the question without a second
`zk_read_note` round-trip. Pure change inside `build`; law: every backlink context
actually contains the link (soundness).

### 7.11 Semantic serendipity: sample the mid-similarity band (InfraNodus)

InfraNodus's thesis is that insight lives in a network's *structural gaps*. The wiki's
`random_target` is uniform; upgrade it to sample note **pairs in the 0.2–0.5 cosine
band** (related enough to be combinable, distant enough to be non-obvious) and, once
§6.5 lands, *across community boundaries*. Render as a daily "collision" panel: two
notes + their nearest shared terms. Zero new infrastructure — `vectors_for` and
`cosine_sparse` exist; determinism via seeding from the day + HEAD commit rather than
`Random.self_init`.

### 7.12 Memex trails: curated paths as first-class notes (Bush, 1945 → 2026)

The spanning-forest `reading_order` is an *automatic* linearization; trails are the
*curated* complement — a `type: trail` note whose body is an ordered slug list,
rendered as a stepper (prev/next within the trail) and served as `zk_trail(slug)` for
agent onboarding ("the SMP-narrowing trail", "the conformance-protocol trail"). Laws:
every trail entry resolves (no dead steps — reuses the existing closure check);
trails are sequences, not cycles.

### 7.13 Community summary notes (Microsoft GraphRAG's "global questions" answer)

Microsoft GraphRAG's distinctive capability is answering corpus-global questions from
**pre-computed community summaries**. Once §6.5's deterministic communities exist, each
community gets a *drafted* MoC/summary note — written by an agent through the §6.2
write path (never inline in the gate), `status: draft` until human-promoted, and
regenerated only when its community's membership hash changes (SQLite-memoized, the
§2.3 circuit-breaker discipline). Global questions ("what does this system believe
about determinism?") then resolve against ~10 summaries instead of ~130 notes.

### 8.2 ACH / Devil's Advocate / Reality / Formal checks, per major cluster

**Cluster R — Retrieval (PPR + BM25/RRF + block vectors).**
*ACH:* H1 flat TF-IDF KNN suffices at 130 notes; H2 PPR+hybrid materially helps agents;
H3 only neural embeddings would help. Evidence: agent queries are dominated by exact
identifiers (slice names, `DIVERGENCE 614`, BIF names) that embeddings blur (favors
BM25), and by "what relates to X" hops (favors graph/PPR); H3 has no failing benchmark
to justify it. **Verdict: H2**, with H1 acceptable until an agent is actually observed
missing recall.
*Devil's advocate:* you're adding three rankers with zero measured recall failures —
classic speculative infrastructure. *Counter:* accepted for BM25 (fold into PPR slice
only if a real miss is logged in the ledger first); PPR stands on its own as ~20 lines
against an existing QCheck'd kernel.
*Reality check:* corpus fits in L2 cache; any of these run in microseconds; the only
real cost is law-suite maintenance.
*Formal check:* PPR inherits the existing Σ=1 stochasticity QCheck law with a teleport
parameter; degeneration law (uniform teleport ⇒ current PageRank) makes the old
behavior the oracle of the new. RRF: unanimity + self-fusion-identity laws (§7.2).

**Cluster T — Temporal (git bi-temporal graph).**
*ACH:* H1 nobody will ask as-of questions; H2 as-of queries + churn-driven decay carry
real value. Evidence for H2: this very repo routinely reasons about *when* a belief
changed (DIVERGENCE entries are exactly that, hand-maintained); §7.3 mechanizes it.
*Devil's advocate:* `git log --follow -p` over the docs tree is the first genuinely
slow component proposed (seconds, not µs), and renames/rewrites make edge attribution
fuzzy. *Counter:* run only in `--wiki-audit` (already off the fast path), memoize per
commit in SQLite, and state the honesty bound: attribution is *best-effort under
renames* — recorded as a documented limit, not hidden.
*Reality check:* medium slice, not small; schedule after the MCP read surface proves
agent demand.
*Formal check:* interval well-formedness, `asof(HEAD) = current` round-trip,
append-only monotonicity — all QCheck-able against synthetic git histories built in a
temp repo by the OCaml test shell.

**Cluster A — Argumentation (discourse types + Dung semantics).**
*ACH:* H1 frontmatter `type:` + typed edges alone (structure without semantics) already
deliver the value; H2 full grounded-extension computation adds decision-support worth
its code. **Verdict: land H1 first (near-zero cost), H2 second** — the grounded
extension is ~60 lines of pure fixpoint OCaml and turns "this decision's support was
undermined" into a *computed* report-only anomaly.
*Devil's advocate:* Dung semantics on a hand-typed graph is formal-methods cosplay —
garbage-in, theorem-out; authors will mistype edges. *Counter:* partially conceded —
which is exactly why the output is report-only anomaly + review queue, never gate-red;
schema validation (§7.6) narrows the garbage; and even mistyped edges surface for
correction precisely *because* the extension computation flags them.
*Reality check:* the epistemically honest framing is decision *support*; the human
stays the judge.
*Formal check:* the grounded extension is the ⊆-least fixpoint of the characteristic
function — laws: uniqueness/determinism, admissibility (no member attacked by an
unattacked node), conflict-freeness, and fixpoint stability (`F(E)=E`). This cluster
carries the strongest formal guarantees in the whole catalogue.

**Cluster Q — zkquery (saved queries as notes).**
*ACH:* H1 grep + existing index pages suffice; H2 a total DSL pays rent. Evidence for
H2: agents currently must parse HTML or call several tools to answer "all flagged
ADRs"; one structured query tool collapses that.
*Devil's advocate:* every project DSL becomes an unmaintained parser with one user.
*Counter:* the grammar is deliberately non-recursive (from/where/sort/limit — no joins,
no subqueries, v1 forever until a logged need), the parser is combinator-style ~80
lines, and it is *the same* query shape Obsidian Bases just standardized — convergent
evolution, not invention.
*Formal check:* totality (non-recursive grammar ⇒ structural termination), filter
commutativity, `limit` monotonicity; semi-naive incrementality (per §8.1) is available
later without changing the surface syntax.

**Cluster M — Memory (session notes; A-MEM inverted).**
*Devil's advocate — taken seriously:* auto-generated notes are how a Zettelkasten dies;
100 template-identical session notes drown the 130 curated ones and poison search,
PageRank, and mentions. *Resolution (this changes the §7.4 design):* session notes get

vectors, and mention-scan by default** (included only under an explicit
`include=episodic` query flag), and are compacted — one note per *slice*, updated in
place via the etag path, not one per run.
*Formal check:* projection law — the wiki graph restricted to non-episodic notes is
byte-identical to the graph with episodic notes absent (episodic memory is a
conservative extension).

**Cluster I — Incremental build (SAC) + Irmin/MRDT storage.**
*Reality check, applied to ourselves:* at 130 notes the full rebuild is milliseconds —
SAC is *not yet justified*; and swapping the storage layer to Irmin is a

### 8.3 The full fractal specification (algebra of the enhanced ZK)

**Carrier sets.** `Note` (slug × typed-meta × blocks), `Block` (stable id × tokens),
`Edge = Untyped | Typed of relation | Mention | Inferred`, `Vec` (ℝ²⁵⁶, F32),
`Interval` (commit × commit option), `Query` (the zkquery AST), `Extension ⊆ Note`.

**Signature (final encoding = the OCaml module type; each op names its law family):**

```ocaml
module type ZK = sig
  val build     : (path * string) list -> page list          (* existing; total *)
  val ppr       : ?teleport:(slug * float) list -> page list -> (slug * float) list
                  (* LAW ppr-degeneration: teleport=[] ⇒ pagerank.  LAW Σ=1. *)
  val bm25      : page list -> query:string -> (slug * float) list
  val rrf       : (slug * float) list list -> (slug * float) list
                  (* LAW rrf-unanimity; LAW rrf-self-identity (order-equiv). *)
  val chunks    : page -> (block_id * string) list
                  (* LAW chunk-partition: concat ∘ chunks ≡ tokens ∘ body. *)
  val asof      : commit -> edge_history -> graph
                  (* LAW asof-head-roundtrip; LAW interval-wellformed. *)
  val grounded  : graph -> Extension.t
                  (* LAW grounded-unique-fixpoint; LAW conflict-free; LAW admissible. *)
  val query     : Query.t -> page list -> row list
                  (* LAW query-total; LAW limit-monotone; LAW filter-commute. *)
  val communities : graph -> (slug * cluster) list
                  (* LAW partition-valid; LAW deterministic (fixed order + tiebreak). *)
end
```

**Oracle vs final, per new op.** `ppr`: oracle = existing `pagerank_core` under the
degeneration law. `bm25`/`rrf`: oracle = brute-force rescore of the whole corpus (no
index) — final may later add postings lists; homomorphism = identical rankings.
`chunks`: oracle = whole-note-as-one-chunk (file-level embedding *is* the initial
encoding); law = block search never ranks the true parent below file-level search.
`asof`: oracle = literally `git checkout <commit>` + `build` in a temp dir (slow,
obviously correct); final = interval algebra over `edge_history`; homomorphism =
graph-equality on sampled commits. `grounded`: oracle = naive iterate-to-fixpoint over
the powerset-free characteristic function (it *is* polynomial; oracle and final
coincide initially). `query`: oracle = `List.filter/sort/take` composition; final may
memoize. `communities`: oracle = fixed-seed reference run; determinism law makes
oracle=final.

**Stratum mapping.** All ops above are **Stratum A** (pure, law-governed, in
`docs_wiki.ml` / a new `zk_algebra.ml`). The shells — git mining, SQLite persistence,
MCP dispatch, agent-driven LLM drafting — are **Stratum B** engines verified
differentially against Stratum A. External LLM calls are **Stratum C**: quarantined,
memoized, circuit-broken, and *no Stratum-A law may depend on their output* (a drafted
MoC is `draft` until a human or a deterministic check promotes it).

**STPA delta.** Two controller changes, each requiring a §10 safety packet before
landing: **CTRL-ZK-AUTHOR gains an MCP entry surface** (UCAs: unvalidated path
traversal — mitigated by existing `path_is_safe`; write flood — rate/size caps;
stale-etag clobber — existing 409 guard extends unchanged) and a new **CTRL-ZK-EPISODIC**
(the harness writing session notes; UCAs: unbounded growth — one-note-per-slice
compaction; search poisoning — the Cluster-M projection law; wrong attribution —
`verified_by: harness` is machine-set, never spoofable from note content). The Rete
gate's semantics are untouched by construction: every new fact class introduced here
(`note_stale`, `structural_hole`, `undermined_decision`) is report-only.
