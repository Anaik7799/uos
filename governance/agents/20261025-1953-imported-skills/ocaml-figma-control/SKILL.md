# OCaml Figma Control

Read `docs/ontology/FIGMA_OCAML_DESIGN_CONTRACT.json` and
`docs/ontology/INFRANODUS_OCAML_AUTHORITY.md`. Pair this skill with
`mobile-first-adaptive-ui`, `algebra-driven-ocaml`, and
`ocaml-playwright-control`.

## Authority Boundary

- `harness/figma_design.ml` is the source of truth for modes, tokens,
  breakpoints, components, screens, transitions, and accessibility bounds.
- Figma and its MCP/plugin APIs are external editable interpretations. They
  may materialize and inspect the OCaml contract; they do not redefine it.
- Never claim that Figma's internal control plane is directly OCaml-owned.
  Plugin/MCP execution is external JavaScript. Any repository browser code is
  still generated by `js_of_ocaml`; no authored JavaScript or TypeScript is
  admitted.
- Database state never passes through Figma. Application persistence remains
  Dream -> `Workspace_store` -> harness `Db` actor -> SQLite.

## Fractal Workflow

1. **Ontology:** classify every token, mode, breakpoint, component, slot,
   screen, transition, state, and observation.
2. **Signature:** add the smallest OCaml constructors and observers needed to
   express those concepts without Figma IDs.
3. **Laws:** establish alias totality, scope correctness, breakpoint order,
   minimum target size, component/state completeness, responsive composition,
   and initial/final observational equivalence.
4. **Interpretations:** keep an OCaml initial operation list and canonical
   final catalog; materialize the latter in Figma through the MCP.
5. **Verification:** validate the OCaml JSON contract, inspect Figma metadata
   and screenshots, then verify the rendered Bonsai UI through direct OCaml
   Playwright at every canonical viewport.

## Figma Construction Order

1. Create or identify one target file and record its key and URL.
2. Inspect attached libraries before creating local primitives.
3. Create primitive variables, semantic aliases, Light/Dark modes, scopes,
   and code syntax. Reject broken aliases.
4. Create typography/effect styles and a Foundations page.
5. Build components one at a time with variants, properties, auto layout,
   focus/disabled/error/loading states, and 44px minimum interactive targets.
6. Compose screens from instances, not detached copies. Cover compact,
   medium, expanded, and large layouts.
7. Add prototype transitions only when they correspond to an OCaml transition
   contract.
8. Render screenshots and inspect metadata after each phase. Record incomplete
   Figma materialization as pending even when the OCaml contract is complete.

## Required Laws

- **Alias totality:** every semantic alias resolves to a primitive in every
  mode.
- **Mode agreement:** Light and Dark expose the same semantic token names.
- **Breakpoint monotonicity:** compact < medium < expanded < large.
- **Target floor:** every interactive component has a minimum target >= 44px.
- **Component closure:** every screen dependency names a registered component.
- **Transition closure:** every transition source/target names a registered
  screen or component state.
- **Homomorphism:** observing the initial and canonical final encodings yields
  the same modes, tokens, components, screens, transitions, and breakpoints.
- **Runtime agreement:** the Bonsai DOM at each viewport satisfies the same
  responsive and accessibility observations as the design contract.

## Evidence And Honesty

Preserve the Figma file key, rendered node screenshots, generated OCaml JSON,
Playwright PNG/WebM/trace artifacts, seeds, and mutant results. Use
`Implemented` only when the repository contains executable evidence. A Figma
frame alone proves design materialization, not runtime behavior or product
parity.
